  How the service works. Spring Boot 3.2.5 on Java 17 with an in-memory H2
  database. On every boot, schema.sql drops and recreates the three tables and
  data.sql seeds them, so schema.sql is the only schema source. Each redemption
  writes one row to the redemption table with the voucher, campaign and user.
  The redeem flow in VoucherService.java
  (voucher-service/src/main/java/com/prizm/campaign/service/VoucherService.java)
  looks up the voucher, rejects if missing, redeemed or void, rejects if the
  campaign is inactive or out of stock, then marks the voucher redeemed,
  decrements stock, inserts the redemption row and fires a best-effort audit
  call. It has no transaction. Every outcome is HTTP 200 with a body of either
  result OK or result FAILED plus a message. Voiding a voucher only flips its
  status and leaves stock and the redemption row alone. The seed gives user-99
  two redemption rows on campaign 1, one on a REDEEMED voucher and one on a VOID
  voucher. The existing tests share live seed state with no rollback, and one
  of them consumes RAYA-0001 for user-1.

  Proposed design

  1. Store the limit on the campaign. Add a column to the campaign table in
     schema.sql: max_redemptions_per_user INT NOT NULL DEFAULT 2, plus the
     matching field and accessors on the Campaign entity. The seed inserts don't
     list the column, so all existing campaigns get 2 from the database default
     with no change to data.sql.
  2. Count from the redemption table. Add a derived query
     countByCampaignIdAndUserId to the redemption repository. One extra query
     per redeem, no new table, no new dependency, and the table already records
     exactly what we need.
  3. Enforce in the service. In the redeem method, after the existing checks and
     before any write, compare the count to the campaign's limit. If the user
     is at or over it, return the existing FAILED shape with a message like User
     has reached the redemption limit for this campaign (2). The number comes
     from the campaign, so a campaign with a different limit reports its own.
  4. Tests. A new test class covering: existing campaign defaults to 2; user-99
     rejected on campaign 1; a new user redeems twice then is rejected on the
     third; user-99 still succeeds on campaign 2; a rejected attempt leaves
     stock and the voucher untouched. Each test rolls back so nothing leaks into
     the existing tests, and I'll avoid RAYA-0001 since the existing suite
     consumes it. I'll show per-test results by parsing Gradle's XML reports
     rather than changing build.gradle.
  5. Commit sequence. Import starter, schema and entity change, repository count
     query, service check, tests, docs. Each pushed to dev as it lands.
